Interview field guide · v0.1.0

把招聘信息，变成可行动的数据。

JobPostings 是一个运行在 Windows 本机的招聘信息聚合与求职进度管理系统。它把微信群、网页和文件里的非结构化信息，经过解析、模型识别、证据留存和人工审核，整理成企业、岗位、招聘事件和个人求职进度。

Local-first React + TypeScript FastAPI + Python SQLite Codex / LLM
J 30 秒项目介绍

“我做的是一个本地优先的招聘信息工作台。前端用 React 和 TypeScript，后端用 FastAPI，数据落在 SQLite。系统从 TraceMemo、公开 URL 和文件接收原始材料，经过队列、网页/文档解析、OCR 和 Codex 结构化，最后保存带来源证据的岗位目录，并通过 SSE 让前端实时刷新。”

项目定位 架构链路 技术栈 处理流程 设计取舍 面试问答

01 · Positioning

先把项目讲成一个产品问题

面试官不需要先听依赖清单，先让对方明白：为什么要做、数据从哪里来、系统帮用户减少了什么麻烦。

01

Local-first

核心数据、附件和密钥默认保存在本机。没有单独部署 MySQL 或云数据库也能运行，更适合包含个人求职记录的场景。

02

Evidence-first

模型抽取出来的企业、岗位和活动不会脱离原始消息。系统保留来源、附件、版本和证据，遇到不确定内容进入人工审核。

03

Human-in-the-loop

模型适合做语义分类和结构化，但不负责替用户“猜事实”。低置信度、冲突和归并异常会留在审核边界内。

02 · Architecture

一张图看懂系统如何协作

可以沿着箭头讲：输入先被保存，再异步处理，模型只负责语义判断，目录层负责稳定地写入和去重。

01 / INPUT

消息与文件

TraceMemo 群聊、文本、公开 URL、PDF/DOCX/XLSX、图片。

FastAPI 接入

03 / QUEUE

持久化队列

processing_jobs 记录状态、阶段日志、重试和取消。

04 / EXTRACT

BeautifulSoup、Playwright、文档解析、Codex OCR 与本地兜底。

05 / MODEL

语义结构化

Codex 或 OpenAI-compatible 模型输出严格 JSON。

06 / CATALOG

目录与证据

写入企业、岗位、事件、版本、证据和审核项。

07 / UI

浏览器工作台

React 页面读取 API，SSE 通知处理进度并刷新目录。

关键边界：解析器负责“把材料读出来”，模型负责“理解招聘语义”，目录层负责“保存、归并和去重”。这样可以避免把本地关键词规则误当成招聘事实。

03 · Stack

技术栈：每一项都对应一个实际问题

面试时不要只报名称，可以顺带说出“它在这里解决什么问题”。

浏览器前端frontend/
  • React 19
  • TypeScript 5.9
  • Vite 7
  • Motion
  • Fetch / EventSource
  • CSS

React 管理页面和交互状态，TypeScript 约束数据形状，Vite 负责开发服务器和生产构建。当前是手写 React/CSS，没有引入大型 UI 组件库；后端 API 通过 fetch 调用，进度通过原生 EventSource 接收 SSE。

后端 API 与运行时backend/app/
  • Python 3.12+
  • FastAPI
  • Uvicorn
  • Pydantic 2
  • httpx
  • asyncio

FastAPI 集中提供 REST API、鉴权和静态前端服务；Pydantic 做请求模型和配置校验；Uvicorn 负责运行。生命周期里启动 worker、同步、通知、备份等后台循环，阻塞型处理通过 asyncio.to_thread 移出事件循环。

数据存储db.py + local storage
  • SQLite
  • sqlite3
  • Schema migration
  • Blob files
  • JSON fields

SQLite 适配单机、低运维和隐私优先的目标。结构化数据在数据库中，原始附件放在本地 Blob 目录；schema_meta 和兼容性迁移保证旧数据库升级时不被直接丢弃。

解析、浏览器与文件parsers.py / browser.py
  • BeautifulSoup
  • Playwright
  • openpyxl
  • PyMuPDF
  • python-docx
  • OpenCV

静态网页用 BeautifulSoup 提取；遇到动态网页或懒加载图片时用 Playwright 渲染；XLSX、PDF、DOCX 走对应解析器，图片保留 OCR 和二维码结果。旧版 DOC/XLS 需要目标机额外安装转换器。

AI 与语义处理codex_agent.py / model_provider.py
  • Local Codex CLI
  • OpenAI-compatible API
  • Markdown prompts
  • Strict JSON
  • Redaction
  • Token budget

默认优先使用本地 Codex；也支持 Chat Completions 或 Responses API。任务 prompt 明确输入和输出 schema，模型做招聘分类、字段抽取和语义去重，结果再由后端校验并写入目录。

安全与桌面发布security.py / desktop/
  • HttpOnly Cookie
  • Scope authorization
  • DPAPI
  • cryptography
  • PyInstaller
  • WebDAV

后端权限依赖是安全边界，前端隐藏页面不是安全措施；敏感配置保存在本机安全存储，支持加密备份。Windows 通过桌面启动器、托盘和 PyInstaller 打包，可选 Inno Setup 生成安装器。

04 · Data flow

按一次“导入”来讲完整处理流程

这部分最适合回答“你具体负责了什么”或“一个招聘信息进来之后发生了什么”。

01

接收并保留原始材料

TraceMemo 消息或手工导入先进入 raw_messages；文件进入 artifacts。通过外部消息 ID 或内容指纹避免重复接收。

02

创建可恢复的处理任务

系统创建 processing_jobs，记录 queued、extracting、classifying、review、completed 等阶段，并保留日志、重试和取消状态。

03

提取正文、图片和元数据

解析 URL、文件和消息内容；动态网页由 Playwright 渲染。图片默认走本地 Codex OCR，Codex 不可用或无可读文字时才使用可选的 RapidOCR 兜底。

04

让模型输出结构化结果

后端用任务专用 prompt 调用 Codex 或通用模型，要求严格 JSON。输出区分企业、招聘批次、共享招聘条件、具体岗位、招聘事件和证据。

05

校验、归并、去重并写入目录

catalog.py 负责稳定写入和关联证据；岗位、企业和事件分别处理，不把“专业、福利或企业介绍”误写成岗位。冲突或低置信度结果进入审核。

06

通过 SSE 告知前端

前端监听 /api/v1/events 的 job.updated、processing.updated 等事件，刷新页面数据，让用户看到任务状态而不是等待一个黑盒请求。

05 · Trade-offs

几个能体现工程思考的设计取舍

Q

为什么选择 SQLite，而不是 PostgreSQL？

产品是 Windows 本地优先，目标用户和并发规模都不要求独立数据库服务。SQLite 部署简单、数据文件可备份，能降低使用门槛；如果未来变成多用户高并发服务，再考虑迁移到服务型数据库。

Q

为什么不能只用关键词规则？

招聘消息格式不稳定，企业介绍、福利、专业要求和岗位标题可能挨在一起。规则可以做格式和安全校验，但语义归类交给模型；这样减少“看见一个词就生成一个岗位”的误判。

Q

如何处理模型不确定或重复的结果？

原始消息和证据始终保留；不确定字段使用空值或进入审核，不强行猜测。目录层维护实体关系、版本和去重逻辑，明确时间或地点冲突的事件不自动合并。

Q

为什么要做队列和 SSE？

网页渲染、OCR、模型请求都可能耗时，不能让一次 HTTP 请求长时间卡住界面。队列让任务可重试、可取消、可观察；SSE 让前端及时获得状态变化，交互更可靠。

06 · Data model

数据不是一张“岗位表”，而是分层的事实链

这种拆分既方便展示，也方便解释“模型判断”和“来源事实”之间的边界。

层次保存什么为什么单独保存
来源层raw_messages、artifacts、TraceMemo 缓存、原始 URL保留可追溯的事实和附件，不让后续模型结果覆盖原文。
处理层processing_jobs、processing_logs、llm_calls观察任务阶段、重试、Token 用量、失败原因和审核载荷。
招聘目录层companies、jobs、recruitment_events、evidences把企业、岗位、活动和证据拆开，支持版本、归并与去重。
用户层user_job_states、备注、标签、关注、通知、申请事件把招聘事实和“我对这个岗位做了什么”分离，支持个人求职进度。

07 · Safety

隐私和安全：面试时要主动讲清楚

最小暴露

默认本地保存数据和附件；使用云模型时可开启手机号、邮箱、微信号、QQ、身份证号的稳定占位符脱敏，原始消息不被覆盖。

不可信输入

网页正文和群聊内容始终按不可信数据处理，不能改变系统提示、权限或任务流程；公开 URL 还要经过安全校验。

可恢复运维

破坏性维护先备份，队列、失败原因和证据边界要保留。模型额度达到上限时暂停新请求，避免无控制地继续消耗。

08 · Interview kit

可以直接练习的回答

这个项目解决的是招聘信息碎片化的问题。用户可能从微信群、网页、PDF 或图片里看到招聘内容，我把这些输入统一保存为原始来源，再通过 FastAPI 后端创建可恢复的处理任务。解析器负责提取正文和附件，Playwright 处理动态网页，Codex 负责招聘语义识别和严格 JSON 输出，最后由目录层分别保存企业、岗位、招聘事件和证据。前端用 React + TypeScript 展示结果，通过 SSE 获取处理进度。由于招聘信息包含个人隐私且项目主要是单机使用，所以选择 SQLite 和本地优先设计，并把不确定结果留给人工审核。

适合 1–2 分钟的项目概述；可以按面试官追问再展开技术细节。

“你在这个项目中最看重什么？”

我最看重的是数据可追溯性。模型可以提高非结构化文本的处理效率，但不能替代来源事实，所以系统把原始消息、附件、证据和版本保留下来，并把低置信度结果交给审核。

“如果规模扩大，你会怎么演进？”

先把处理器和 API 的边界保持稳定，再把 SQLite 替换成 PostgreSQL，把本地队列拆成独立 worker，并把 Blob 放到对象存储；SSE 也可以根据部署形态改成消息总线或 WebSocket。

“如何验证项目质量？”

前端运行 TypeScript 检查和 Vite build；后端按解析、TraceMemo、处理、API 等边界跑定向 pytest。外部 TraceMemo、模型、SMTP、AList 和安装流程还需要在目标环境做真实冒烟测试。

“项目有什么现实限制？”

本地 Codex 需要目标机已安装并登录 CLI；旧版 DOC/XLS 需要额外转换器；开发版和安装版默认数据目录不同；Windows 临时目录权限也可能影响完整测试收尾。

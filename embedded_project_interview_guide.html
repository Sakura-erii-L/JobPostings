先记住三条面试原则

左侧菜单可以逐层展开；代码中的函数名、变量名和参数保留原文，方便你回到工程核对。

讲工程链路

不要只说“用了 STM32、PID、传感器”。要说清楚输入在哪里采样、多久更新一次、怎样转成左右轮目标、怎样限幅、怎样停机。

讲真实边界

源码能证明“实现了哪些机制”，但不能自动证明你的个人分工、比赛名次或成功率。没有数据就不编数据；没有主导就不说主导。

讲一个难点

每个项目至少准备一个“现象 → 定位 → 修改/调参 → 验证”的故事。面试官往往通过这个故事判断你是否真正上过车。

个人分工提示：我能从源码还原系统结构，但不能从目录判断你个人负责了哪些模块。下面的第一人称段落是可编辑模板：只有你确实做过的部分才用“我负责/我实现”，其余改成“我参与/我了解”。
PROJECT 01 · STM32F4

国赛寻宝：四轮闭环 + 多传感器赛场车

推荐作为“嵌入式软件 / 运动控制 / 底层驱动”主项目。

一句话定位

这是一个基于 STM32F4 的场地任务车：通过 8 路激光/红外传感器循迹，通过四路编码器做独立车轮速度闭环，通过 JY901 姿态角辅助直行、坡面和转向，再由二维码平台信息和门状态决定路线。

源码：D:\Projects\比赛\国赛寻宝\总程序\USER\main.c；HARDWARE\Encoder、Motor、Trailing、Mission

不要这样说

“就是让小车沿黑线跑，然后到几个点停一下。”

应该这样说

我把系统拆成了实时运动控制层和上层任务层。运动控制层在固定周期采样编码器和传感器，生成四个车轮的 PWM；任务层把坡面、跷跷板、门、二维码路线等赛道元素封装成可组合的动作函数，并在门不可通行时回退到下一条路径。

P1 · MOTION CONTROL

最值得展开的底层：四轮速度闭环

这是你从“会调用库”升级到“理解控制链”的核心。

1. PWM 输出

  • Motor_Init() 开启 TIM1/TIM8 与 GPIOA/GPIOC 复用。
  • 注释给出的通道映射：PA8–PA11 和 PC6–PC9，共 8 个比较通道。
  • 预分频 56 - 1、周期 300 - 1，按源码注释对应约 10 kHz PWM。
  • Motor_control() 先把输入限制在 ±PWM_limit，再用正负号选择 H 桥方向通道。

2. 10 ms 采样

  • TIM2–TIM5 工作在 encoder interface，计数器从 HALF_ARR 中点开始。
  • TIM9 预分频 167、周期 9999，源码按 168 MHz 定时为 10 ms 更新。
  • 中断读取计数器相对中点的变化，左右轮根据安装方向做符号统一，然后立即把计数器回到中点。
  • 这样得到的是“过去 10 ms 的脉冲变化”，而不是累计计数器溢出后的绝对值。

3. 四个轮子分别算误差

源码把目标速度换算成目标脉冲量，再减去实际脉冲对应量。以左前轮为例，代码形式是：

error_left_front = left_speed * 44
                    - Pulsedete_Left_front * 115.385;

之后在 REAL_PID 分支中维护四个通道各自的 integral[]、derivative[]、上次误差和上次控制量：

Control_i = Kp[i] * error_i
          + Ki[i] * integral[i]
          + Kd[i] * derivative[i]
          + Control_i_last;
为什么四路独立四个轮子的摩擦、负载、安装误差不完全相同；独立反馈可以让左右侧和前后轮的速度更一致。
为什么要限幅控制量限制在源码的 ±10000，随后按 0.015 缩放成 PWM；避免积分/瞬态误差把输出推到不可控范围。
低脉冲特殊处理当某轮脉冲绝对值小于 2，源码用比例补偿并清积分，减少静止/低速时积分累积。
HARDWARE\Encoder\Encoder.h:9-71；HARDWARE\Encoder\Encoder.c:250-517

4. 距离闭环如何服务任务层

until_distance(exp) 和 can_go_distance(exp, timeout_ms) 把四轮脉冲的平均值换算为距离。公式使用了源码中的 52、44、轮径 10.4 和 π。前者等待达到目标距离；后者额外检查超时和 OBSTACLE，返回成功/失败。任务层因此可以说“前进 55 cm 后判断门是否允许通过”，而不是只用固定延时。

可直接说的控制细节

“我的路线函数不是每一段都重新写一套电机控制，而是修改全局的速度目标和循迹模式。10 ms 中断统一读取当前模式，执行同一套差速和 PID，这样路线层只负责策略，控制层负责实时性。”

不要夸大的地方

源码里是加权差速 + 四轮速度 PID，并没有看到完整的模型预测、卡尔曼滤波或视觉定位。可以说“多传感器融合了线、距离和姿态条件”，不要说成高级自主导航。

P1 · ROBUSTNESS

最能体现工程思维的地方：门状态和回退

不是“撞一下再试”，而是一次探测结果会影响后续路线。

door_flag[1..4] 的三态语义

  • 0：未知，还没有验证。
  • 1：已验证可通行。
  • -1：已验证不可通行。

全局初值是 {1,0,0,0,0}，第 0 位未使用；函数通过实际尝试逐步填充门状态。

judge_left_door() 的约束推理

遍历 1–4 号门：如果已经确认 2 个可通行，则把剩余未知门推断为不可通行；如果已经确认 2 个不可通行，则把剩余未知门推断为可通行。这利用了赛题对门状态数量的约束，把一次试探结果转化成全局信息。

part_door() 的可讲流程

进入门区切换到陀螺仪直行或限制循迹，降低路线不确定性。
接近门按 calc_times(order_speed, 55.0f) 估算通过窗口。
碰撞监测循环期间检测 COLLISION，碰撞则提前结束尝试。
结果更新无碰撞：标记 1；碰撞：标记 -1 并后退。
换门/汇合回退到分叉点，尝试下一扇门，最后进入共同路径。

我参与开发过一个基于 STM32F4 的寻宝赛场地车控制系统，主要可以从运动控制和任务编排两层介绍。底层使用 TIM1/TIM8 输出四个电机的 H 桥 PWM，TIM2 到 TIM5 读取四路编码器，并由 TIM9 以 10 ms 周期更新四轮速度 PID，因此左右前后轮可以分别补偿。循迹部分有 8 路激光传感器，根据普通、限制、左右转和陀螺仪直行等模式生成左右目标速度；JY901 通过 USART3 输入姿态角，用于直行、坡面和跷跷板判断。上层把每一段赛道封装成 pathX_Y()，通过二维码得到平台序列，再结合 door_flag 的未知/可通行/不可通行三态决定过门路线；如果碰撞，就后退并切换下一扇门。我认为这个项目最有价值的地方是把传感器、闭环控制和比赛策略串成了一条完整链路。

继续展开时：优先展开“10 ms 编码器闭环”或“门状态回退”其中一个，不要在 60 秒里把每个赛道障碍都念一遍。
P1 · FOLLOW-UP QUESTIONS

国赛寻宝：面试官可能继续问什么

回答结构：现象 → 原因 → 代码/参数 → 验证。
为什么要四路独立 PID？左右侧一个 PID 不够吗？
四个轮子的机械阻力和负载不一致，尤其在转弯、上坡、载荷变化时，前后轮的实际脉冲可能不同。源码分别保存四路 error、积分、微分和控制量，再统一映射到 PWM，能把每个轮子的速度误差单独压下去。左右侧差速是上层运动意图，四路 PID 是底层执行补偿，两者不是同一层。
为什么速度环用 10 ms？周期太快或太慢会怎样？
10 ms 是源码里 TIM9 的固定更新周期，能在车辆运动变化和编码器脉冲分辨率之间取得折中。周期太快，低速时一个周期内脉冲太少，误差抖动明显；周期太慢，转弯和负载变化响应会滞后。实际调参还要结合编码器分辨率、最高车速和控制量饱和观察，而不是只背“10 ms 是标准答案”。
为什么既有激光循迹，又有陀螺仪？
激光适合识别线的位置和路口，陀螺仪适合在坡面、断线、原地旋转或需要保持航向的阶段提供角度信息。源码通过 State_Gyro_straight、turn_angle() 和条件函数把两类输入放在不同阶段使用，不是简单把两者数值直接相加。
门判断是不是纯延时？
不完全是。part_door() 会用 calc_times() 给出一个时间窗口，但窗口内持续检查碰撞；无碰撞就标记可通过，碰撞就标记不可通过、后退并尝试其他门。源码还用 judge_left_door() 根据已知的两开/两关约束推断剩余门状态。
这个项目的不足是什么？
当前实现有明显的比赛型特征：任务函数里存在阻塞等待，部分等待条件没有显式超时；控制、显示和任务状态耦合较多；传感器初始化与读取端口存在需要复核的版本不一致。我会在产品化版本中引入显式状态机、统一的超时/取消/急停接口，把控制周期和任务周期解耦，并补充硬件在环日志。

白平衡的逻辑

  1. RGB_Init() 初始化 TCS3200、Timer3 和外部中断。
  2. 用白色基准分别得到 g_array[0..2]。
  3. 计算 g_SF[0..2] = 255.0 / g_array[i]。
  4. 后续测量将各通道频数乘比例因子，减少传感器通道增益差异。

当前源码的分类阈值

  • 白：R/G/B 原始计数均大于 600。
  • 蓝：B-G > 40 且 B-R > 20。
  • 黑：三通道原始计数和小于 520。
  • 红：R ≥ G+200 且 R ≥ B+150。
  • 绿：G ≥ B-30 且 G ≥ R。
  • 代码用数值 1–5 表示绿/白/红/黑/蓝，0 表示未检测到。

P2 · MOTION & POSITIONING

前进/后退两套循迹 + 数线定位

动作准确性来自“传感器位置 + 参数 + 刹车补偿”的组合。

前进 trackingAHEAD()

  • 把 4 路数字量拼成 4 bit 状态 a，对应左小偏、左中偏、左大偏、右侧对称情况。
  • 误差使用 errorxiao=2.3、errorzhong=2.5、errorda=3.0。
  • 当前参数为 kp=46、ki=0、kd=45，实际是比例 + 微分控制。
  • 将 pid 限制在 ±250，再对左右基础速度做差速修正并限制到 PWM 范围。

后退 trackingBACK()

  • 使用后方 4 路传感器，误差方向和前进相反。
  • 独立参数 v3/v4=45、kp1=10、kd1=3。
  • 大偏差时调用 turnright1()/turnleft1()，小偏差时做差速调节。
  • 原因是倒车时传感器相对车体的位置和运动方向改变，不能简单复用前进控制器。

数线定位的标准动作

预走先运行若干次循迹，避免从起点立即重复计数。
检测边沿用 sensor_10 或 sensor_9 判断线是否出现/离开。
计数每通过一根线，增加 count；再执行 45/50 次控制循环让传感器离开当前线。
末端补偿执行 iii 的继续运动，再用 x 时间的反向力刹车。
停车稳定调用主动/滑行停车并延时，给机构动作留下稳定时间。

因此 count_line_ahead(line, iii, x) 的三个参数分别可以解释为：数几根线、过最后一根后继续多久、反向刹车多久。这个函数把“走到某个物理位置”从纯延时升级成了可重复的传感器定位。

状态数据结构

  • color[1..5]：A/B/C/D/E 物块当前识别到的颜色码。
  • defen[1..5]：按颜色索引累计的分值，F 区加 10，G 区加 100。
  • AAA..EEE：把前一阶段识别结果保存下来，后续 G 区校验/排序。
  • CCC/DDD/EEE：C/D/E 组的历史颜色状态，支持部分抓取失败时继续决策。

D 颜色的补全

在 putFquAB() 中，源码使用 color[4] = 15 - color[1] - color[2] - color[3] - color[5] 做剩余颜色补全，并设置 flag_rgb。这依赖颜色编码 1–5 恰好各出现一次；面试应说“利用赛题颜色集合约束进行推断”，同时承认它依赖前提，产品代码应先验证输入合法性和唯一性。

putFquAB() 的分支讲法

情况源码动作工程解释
A/B 都抓到且颜色有序按较小颜色码到较大颜色码的方向转向，左右钩分别放置，分值各加 10。把颜色码映射为场地方向，减少固定路线分支。
A/B 都抓到但顺序相反先去 B，再去 A，交换左右钩动作和转角差值。根据相对位置动态改变执行顺序。
只抓到 A 或 B保留已抓到物块，单独放置；另一个路径不强行执行。部分成功仍能获得可用结果，避免错误动作扩大损失。
两个都未抓到复位并转向，准备后续路径。失败分支有明确安全退出，而非继续使用未初始化颜色。
颜色冲突进入“将错就错”分支，完成可执行的堆叠/回位。在比赛约束下优先保住系统可运行性，但需要标注为降级策略。

duidie(defenshu)：用组合状态选择机械动作

它根据得分组合 10、100、11、101、110、111 选择不同的套筒升降/开合/释放方案。例如多层堆叠需要在每一层之间抬升套筒、检测物块状态、收紧、定位到目标线、释放，再回到起点。也就是说，duidie() 是一个小型动作调度器，而不是一个简单的 switch。

THREE102577.ino:2171-2300；THREE102577.ino:4452-4458
更稳的面试表述：“我把物块颜色、当前钩子状态和已完成得分保存在数组/变量中，用条件分支决定取放顺序，并把堆叠动作按分值组合封装。”不要说“我做了通用规划器”或“用了最优路径算法”，当前源码体现的是基于规则和赛题约束的组合决策。

P2 · FOLLOW-UP QUESTIONS

光电工程赛：面试官可能继续问什么

重点准备标定、定位、机构时序和失败分支。
TCS3200 为什么要做白平衡？只比较 R/G/B 大小不行吗？
不同通道的传感器增益、光源和安装角度会造成基线不同，直接比较原始频数容易把通道差异当成颜色。源码用白色参考得到三个通道的比例因子，再做归一化。阈值仍然是规则阈值，所以现场还需要通过串口观察频数并重新校准。
为什么前进和后退要两套循迹参数？
后退时传感器位于运动方向的另一侧，车辆对相同的横向偏差的响应方向不同；而且后方传感器的安装距离、线宽和电机低速特性也不同。源码分别维护 v1/v2/kp/kd 与 v3/v4/kp1/kd1，并在大偏差时使用不同的纠偏动作。
数线定位为什么还要时间和反向力？
传感器检测到线时，车辆已经有速度和惯性，立即停会越过目标点；因此函数先数到目标线，再继续一个可调的 iii 时间，最后用 x 时间反向输出做刹车补偿。这个参数需要通过实车反复标定，换电池电压、地面摩擦或载荷后可能要重新调。
你们的 45° 转向是陀螺仪闭环吗？
当前源码更准确的说法是“基于差速电机、定位传感器数线和反向刹车的开环/半闭环动作”。代码读取了 JY901 的 real_angle[2] 并计算目标角，但后续角度误差修正 while 循环被注释掉。我会把陀螺仪修正重新做成带角度误差、超时和最大修正次数的闭环，以解决打滑和地面变化导致的角度误差。
如果抓取失败，代码怎么避免整个任务崩掉？
颜色 0 代表未检测到，putFquAB/putGquAB/putFquCED/putGquCED 分别处理双抓、只抓到一侧、全未抓到、颜色冲突等情况；钩子会复位，车辆通过数线回到可执行节点。改进时我会把这些隐式分支改成显式的 GrabResult、机构状态和超时状态，减少数组里 0 值被误当成有效颜色的风险。
这个项目代码有哪些需要改进的地方？
当前是比赛迭代型单文件：全局变量多、重复动作多、阈值和舵机角度散落、部分函数注释写“有问题”，并且 Scan_Color 的返回类型与返回语句不一致。若产品化，我会拆成颜色传感器、运动控制、定位、机构状态机和任务规划模块，把参数集中到结构体并加入合法性校验、测试模式和故障超时。

面试前最值得补的 5 个验证动作

  1. 把国赛寻宝的四路编码器、PID 误差、PWM 和 calc_distance 的单位在纸上推一遍，能解释每个常数来源。

  4. 从 putCAE() 选一条颜色分支，从 putFquAB() 选“只抓到一侧”分支，手动画出钩子和车辆的动作顺序。

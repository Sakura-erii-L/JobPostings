# 前端设计提案

## 1. 定位与依据

本提案把 JobPostings 定位为“招聘资料工作台”：安静、清晰，方便连续检索招聘信息、核对来源并推进个人求职。依据是 [`docs/FRONTEND_UI_SUMMARY.md`](../docs/FRONTEND_UI_SUMMARY.md) 的静态代码审计，重点参考 `frontend/src/main.tsx`、`styles.css` 和 `queue.css` 中的页面、组件与交互结构。审计没有运行时截图或真实数据验证，因此本文是未来设计提案，不代表视觉或可访问性标准已经实现。

设计将保留现有业务功能、权限边界、React/Vite 架构和页面状态切换，逐步减少深蓝渐变侧栏、重复卡片、胶囊标签、装饰性指标和英文 eyebrow 带来的 SaaS Dashboard 感。信息层级应服务于“找到资料、确认事实、采取下一步”，而不是增加装饰。

## 2. 视觉规范

以下是建议 token，不是当前实现的承诺：画布 `#F7F8FA`，表面 `#FFFFFF`，主文字 `#202733`，次文字 `#596575`，分隔线 `#DDE2E8`，强调色 `#2457A6`。成功、警告和错误只表达状态，必须同时有文字或动作说明，不能依靠颜色单独传达。

不使用渐变；普通内容不加阴影，浮层只使用很弱的阴影。普通控件圆角 6px，独立面板 8px；间距限定为 4/8/12/16/24/32px。使用 `Microsoft YaHei`、`PingFang SC`、`system-ui` 等中文系统字体，不加载外部字体；正文 14px、辅助文字 12px、页面标题 22px，正文行高 1.5，金额、日期和计数可以使用等宽数字。选中项使用浅强调底色、强调文字或竖线；按钮焦点使用 2px 强调色轮廓并保留 2px 偏移。

图标采用少量、统一的线性内联 SVG，并配合文字，不引入组件库或图标依赖。彩色装饰、巨型欢迎头图和没有业务价值的图表不加入。

## 3. 应用壳与操作层级

应用壳使用浅色、约 216px 宽的导航区，以边线与内容分隔。导航分为“求职”：企业与岗位、招聘时间轴、求职进度；管理员可见“数据管理”：导入、待审核、处理队列、管理台。底部放账户安全和管理员设置。管理台快捷入口作为辅助入口保留现有能力，但不与主导航重复争夺注意力。

页面头只保留标题、必要说明和一个主要操作。次要操作使用文字或描边按钮；批量操作在完成选择后出现，低频操作收进“更多”，危险操作与常规操作分隔。现有指标收缩为工具条中的计数，并保留筛选语义。相同条目优先用行间距和分隔线区分；卡片只承载独立任务或独立对象，避免卡片嵌套。

操作文案应描述结果或影响，例如“加入队列（3）”“重试任务”“保存连接设置”，不要只依赖图标。页面头的说明只解释当前任务和数据范围；当用户需要选择对象时，选择数、可用动作和取消入口应在同一操作区域内可见。删除、清除缓存、恢复备份等高影响动作要在确认前说明对象、范围和不可逆影响，确认后提供持久结果。

## 4. 页面方案

| 页面 | 设计方向 |
| --- | --- |
| 企业与岗位 | 默认使用紧凑列表；卡片视图留待后续评估。每行显示名称、行业/地点和岗位数，摘要只使用已有字段，缺失显示“未提供”。搜索、筛选和排序紧邻结果；进入详情后返回时保留搜索、筛选和滚动位置。 |
| 企业详情 | 按“概览 → 招聘公共条件 → 岗位 → 时间轴”组织。企业资料和核查信息按需展开；桌面端来源与证据放独立窄辅栏，窄屏移到相关内容之后。推测必须标为推测，不能显示成事实。 |
| 招聘时间轴 | 以日期分组，使用清晰时间列，保留周视图/列表视图切换；事件类型用轻量标签表达。 |
| 求职进度 | 桌面保留四列：感兴趣、已投递、面试中、Offer；窄屏改为状态 tabs 加单列，可显示各列计数并保留全部状态。 |
| 导入招聘信息 | 三种导入方式使用入口切换，共享结果反馈。群聊流程明确为“选群 → 选消息 → 确认入队”；提交按钮显示数量，入队反馈提供查看队列入口。 |
| 处理队列 | 默认只显示来源摘要、状态、当前步骤、已有字段中的更新时间和下一动作。错误摘要、重试等适用动作直接可见；原文、证据、子任务和日志展开查看。 |
| 待审核 | 原始证据与提取结果并列，窄屏依次排列；完整载荷默认折叠，审核动作始终可见。 |
| 系统设置 | 按连接、处理、存储备份、账户与安全等任务分区，账户页可保持独立。保存与测试各自反馈；危险操作放独立区域，并说明确认对象和影响。管理台沿用列表/表单基础规则，不增加指标大屏。 |

企业和岗位的列表需要让用户先看到名称、地点、岗位数量和更新时间等已有事实，再进入完整资料；不为填满空白而编造摘要。详情中的来源、证据、原始消息和模型提取结果要维持可追溯关系，证据缺失时明确显示缺失。时间轴和队列都应优先服务扫描：先给日期、状态、步骤与下一动作，再让用户展开长文本。求职状态变更后应保留当前筛选和滚动位置，避免用户在连续整理岗位时反复定位。

## 5. 交互与响应式

复用现有 `1000px` 和 `680px` 断点。`681–1000px` 可收窄导航但保留文字；`<=680px` 使用带文字的菜单按钮打开导航抽屉，当前页标题保持可见，并完整处理关闭、焦点返回、Escape 和焦点限制。触摸目标至少 44px，页面不得横向溢出；局部宽表独立滚动。

所有可交互项都可由键盘到达，统一提供 `:focus-visible`；展开按钮声明 `aria-expanded`，图标按钮提供 accessible name。异步按钮保持 loading 状态并防止重复提交；成功用行内确认或低干扰通知，错误就近持久显示并提供重试，避免 `alert` 和遮挡页面头部。长任务以真实队列状态为准。加载、空数据、筛选无结果和失败分开呈现，并给出对应下一步。

焦点顺序应与视觉阅读顺序一致，抽屉打开时焦点先进入关闭按钮或当前页标题，关闭后返回触发菜单的按钮。筛选条件变化要能被键盘感知，状态标签旁同时提供可读文本。网络请求期间不清空已有结果；刷新、重试和取消应说明正在作用的任务。通知不应成为唯一反馈，关键成功或失败需要留在相关表单、行或队列项附近。

## 6. 落地顺序与未来验收

这是未来实施顺序，本次只交付文档。P0 处理 `styles.css`、`main.tsx` 中的应用壳、`NavButton`、`PageHeader`、按钮反馈、焦点和窄屏导航；P1 处理企业列表/详情、`queue.css` 队列、导入和审核；P2 完善设置、时间轴和看板。

未来验收需覆盖 360、680、1000、1440 宽度，普通用户与管理员权限，键盘完整操作，以及“搜索 → 进入详情 → 返回”“群聊导入 → 查看队列”“失败 → 重试”和设置保存失败场景。正文对比度至少 4.5:1，焦点和控件边界至少 3:1。实施后运行 `frontend` 下的 `npm run typecheck` 和 `npm run build`；这些是未来标准，当前没有据此宣称已通过。
